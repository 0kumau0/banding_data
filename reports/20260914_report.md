# 2026-09-14 レポート

## 要約

1. **週末の2条件（A2 / B4）は完走したが、どちらも参照解に届かなかった。**
   対数尤度で約80下の地点。追加反復では現実的な時間で埋まらない
2. **勾配は正しい。** logL は199区間すべてで単調増加し、
   B4 の勾配は既知の最尤解を cos +0.979 で指していた
3. **`loglf` のコストは個体数にほぼ2乗で効いていた。** クマ規模で取った
   「コストは ncell で決まる」は外挿できなかった
4. **その2乗は本家コードの性能バグ**（`ind_cov.minCoeff()` の位置）。
   直せば11.8倍速くなり結果は変わらないが、**論文化の都合で修正しない決定**
5. **「Adam が凍結していたから失敗した」という当日の診断は誤りだった。**
   合成データのほうが18倍深く凍っているのに収束している
6. **合成データは設定の比較に使えない。** 6条件すべてが収束してしまい、
   優劣を判定する力がない

**今日いちばん大きいのは 5 と 6。** 失敗の原因はまだ特定できていない、というのが
正しい現状認識。

## 2. 勾配は正しい

`examples/diagnose_far_runs.R` による trace の診断。

1. **logL が199区間すべてで単調増加**（違反0件、両条件とも）。
   勾配は最初から最後まで上昇方向を向いている
2. **`conn_0` と `conn_agri` は別々に動いている。** 同一の摂動を見ている疑いがあったが、
   勾配の相関 +0.24 / 最大絶対差 3092。同じ量ではない
3. **B4 の直近50反復では、勾配が参照解の方向と cos = +0.979 で一致。**
   既知の最尤解をほぼ真っ直ぐ指している

両ログ冒頭の検算（`loglf = −685.520222 / 差 = −4.707e-08`）も、
尤度計算そのものの健全性を裏づけている。

**「平坦な尾根で区別のつかない方向を歩いていた」という仮説も棄却。**
終点は参照解より約80低く、桁違いに劣る地点にいる。

## 3. この track の前提（ユーザから明示された）

**足環データは BFGS では計算が重すぎて落ちる。それを受けて検討した結果が SGD。**
**BFGS で解けるならこの track は存在しない。**

あわせて、**足環データには変換して持ってくる既知の解が無い**（クマの
`--init transformed` にあたるものが存在しない）ため、**`far` が本番の条件**。
`far` からの収束実証は Step 4 の前提条件そのもの。

CLAUDE.md に「なぜ SGD なのか」の節を新設した。

## 5. 2乗の正体は本家コードの性能バグ

`Rprof` と `gc.time()` で切り分けた（`examples/profile_loglf.R`）。

| 関数 | `nind`=4,800 | `nind`=19,200 | 倍率 |
|---|---|---|---|
| **`pcap_poisson`** | 4.18秒（84.6%） | **54.32秒（96.0%）** | **13倍** |
| `log1m_exp_mat` | 0.28秒 | 1.24秒 | 4.4倍 |
| `<GC>` | 0.30秒 | 0.56秒 | 1.9倍 |
| `advdiff_core` | 0.10秒 | 0.10秒 | **1倍** |

**ガベージコレクション説は棄却**（総時間の1.0%）。

原因は `adcrsgd/secrad.r:313-323` の2点。

1. **`ind_cov.minCoeff()` が最内ループの中にある。** 値はループ不変なのに
   長さ `nind` の縮約が `nmu × nind × neffort` 回評価され、全体が **O(nind²)** になる
2. **`#pragma omp atomic` が不要。** 並列化は `i` のループで各スレッドは
   自分の行にしか書かない。`nind`=19,200 で1.92億回の atomic ＋ false sharing

### 実証（`examples/pcap_bench.R`。`secrad.r` を触らず3版を比較）

| `nind` | 現行 | ①のみ | ①+② | 速度比 |
|---|---|---|---|---|
| 2,400 | 2.06秒 | 0.72秒 | 0.72秒 | 2.9倍 |
| 9,600 | 21.22秒 | 3.83秒 | 3.55秒 | 6.0倍 |
| 19,200 | **83.09秒** | 7.68秒 | **7.02秒** | **11.8倍** |
| 指数 | **1.78** | 1.14 | **1.10** | |

**結果は完全一致（最大絶対差 0）。**

### 決定: 修正しない

**論文化のときに書きにくいため**（ユーザ判断）。本家をそのまま使っていれば
「adcrtest2 を使用」で済む。原著者への連絡も当面保留。

判断材料は `reports/pcap_fix_decision.md` にまとめた
（対比表 / 実際の diff と行数 / 見直すべき条件）。

**帰結**: コストが `nind` の1.78乗のままなので `sampling_rate` が線形より強く効く。
ただし**複数回捕獲個体は毎回全部使う**設計なので、

```
実効 nind = n_multi + sampling_rate × n_single
```

**効果は単回捕獲個体の割合で決まる。** クマ（複数回59 / 単回50）では
rate 0.1 でも 2.6倍にしかならない。
**足環データの複数回/単回の内訳が、`sampling_rate` で買える速度の上限を決める。**

## 6. 「凍結が原因」は誤りだった（この日いちばん重要）

`examples/freeze_compare.R` で、合成データの6条件とクマ2本を同じ指標で並べた。

| | 初期 max\|g\| | 終盤 max\|g\| | step/alpha 終盤 | 最終誤差 |
|---|---|---|---|---|
| 合成/base（`beta2`=0.999） | 242.8 | **0.19** | **0.00276** | **0.0041** ← 収束 |
| 合成/b2_099 | 242.8 | 0.00 | 0.00027 | 0.0002 |
| 合成/b2_090 | 242.8 | 0.27 | 0.09752 | 0.0007 |
| 合成/reset100 | 242.8 | 0.02 | 0.00274 | 0.0003 |
| 合成/alpha_hi | 242.8 | 0.00 | 0.00000 | 0.0001 |
| 合成/b2_099_hi | 242.8 | 0.00 | 0.00000 | 0.0001 |
| **クマ/A2** | 298.4 | **12.27** | 0.05034 | **1.8866** ← 失敗 |
| **クマ/B4** | 298.4 | 2.55 | 0.04846 | 1.9632 |

**合成/base の `step/alpha` は 0.0028 で、クマの 0.050 より18倍小さい。**
それでも誤差 0.004 まで到達している。

**因果を取り違えていた。**

- **小さい step + 小さい勾配 = 収束した**（合成。勾配が 0.19 まで落ちている）
- **小さい step + 大きい勾配 = 異常**（クマ。勾配が 12.27 のまま残っている）

クマの「勾配の減衰比」が小さい（24, 117）のは**勾配が最後まで下がらなかった**から、
合成の比が大きい（1275〜）のは**本当に収束したから**。同じ指標を逆に読んでいた。

### 合成データは設定の比較に使えない

**6条件すべてが収束している**（最終誤差 0.0001〜0.0041）。
`base` でも十分収束する問題であり、**設定の優劣を判定する力がない。**

09-10 の「`beta2`=0.99 + `alpha`×2.5 が最良（326反復 → 106反復）」は、
**全条件が成功する問題の中での速度差**にすぎなかった。
クマ実データは誤差 1.89 で止まっており、2桁違う難しさ。
合成で選んだ設定が実データに移らなかったのは当然だった。

**したがって「合成データで凍結対策を選ぶ」という計画は、このままでは成立しない。**
