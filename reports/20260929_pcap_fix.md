# `pcap_poisson` の修正 — 実施記録

2026-09-14 に「修正しない」と判断した件（`reports/pcap_fix_decision.md`）を、
**2026-09-29 に見直して①だけ適用した。** その記録。

判断材料（原因の特定、プロファイル、案A/案B の比較）は
**`reports/pcap_fix_decision.md` にある。ここでは繰り返さない。**
このレポートは「何を・なぜ・どう検証したか」と、そのあとに分かった新しい実測。

---

## 1. 結論

| | 内容 | 状態 |
|---|---|---|
| **①** | `ind_cov.minCoeff()` をループの外へ（ループ不変式の巻き上げ） | **適用した**（`f40b7b6`） |
| ② | `#pragma omp atomic` の除去 | **適用していない** |

`adcrsgd/secrad.r` は **「本家 ＋ SGD対応4行 ＋ ①の6行」**。

**①は追加3行・書き換え3行**（3関数 × 2行）。**②は見送った。得られるのが 4〜9% だけで、
変更がループの構造の組み替えになるため。**

---

## 2. なぜ判断が変わったのか

2026-09-14 の却下理由は**今も有効**:

> 本家をそのまま使っていれば「adcrtest2 を使用」で済むが、
> ローカルで書き換えると手法の記述と再現性の説明が煩雑になる。

変わったのは**天秤の反対側**。当時の判断対象は「個体109のクマで11.8倍速くなる」
という話だった。**2026-09-29 に足環データの規模を実測した**
（`examples/band_timing.R`、`docs/20260929_作業記録.md`）:

| | クマ | シジュウカラ（実測） | 比 |
|---|---|---|---|
| `nmu`（= `ncell`） | 8,497 | **13,454** | 1.6倍 |
| `nind` | 109 | **33,551** | 308倍 |
| `neffort` | 227 | **4,229** | 18.6倍 |
| 積 | | | **約9,050倍** |

`pcap` のループは `nmu × nind × neffort` なので、**3つとも桁が違う**。
`results/pcap_bench.csv` からの外挿で `loglf` 1回が:

| | 全国 | 関東（943セル） |
|---|---|---|
| **現行コード** | **14.8 日** | 1.6 時間 |
| **①適用後** | 20.5 時間 | **8.8 分** |

**速度の問題ではなく実行可能性の問題に変わった。**
間引き（`--rate`）は解にならない — 複数回捕獲個体は毎回全部使う設計なので
`nind` は 4,587 を下回れず、`rate 0.01` でも現行コードで `loglf` 1回 11.5時間。

**①を入れて初めて、関東規模の解析が現実的な時間に入る**（`loglf` 8.8分 /
SGD 300反復 9.6日）。

## 3. 実際の差分

3つの関数それぞれで、**追加1行・書き換え1行**。

```diff
  	int nind=ind_cov.size();
+ 	const int cov_min = ind_cov.minCoeff();   // 本家は最内ループ内で毎回評価。ループ不変なので外へ（2026-09-29）
  	MatrixXd res= MatrixXd::Zero(nmu,nind);
  ...
  			for(k=0;k<neffort;k++){
- 				colnum = k+neffort*(ind_cov(j)-ind_cov.minCoeff());
+ 				colnum = k+neffort*(ind_cov(j)-cov_min);
```

| 関数 | 追加 | 書き換え | 用途 |
|---|---|---|---|
| `pcap_bin` | `:282` | `:289` | 二項観測。**現在は未使用** |
| **`pcap_poisson`** | **`:312`** | **`:319`** | **これを使っている** |
| `pcap_poisson_debug` | `:342` | `:348` | デバッグ用。`logpcapthist` から呼ばれない |

**使うのは `pcap_poisson` だけだが3つとも直した。**
同じ欠陥を2箇所に残すと、後で `type="binom"` に切り替えた人が罠にはまるため。

### なぜコンパイラがやってくれないのか

`ind_cov` は `const` なので `minCoeff()` の値はループ不変。本来は
**ループ不変式の巻き上げ**（loop-invariant hoisting）としてコンパイラが自動で行う。
`minCoeff()` が Eigen のメソッド呼び出しで、**副作用が無いことを証明できない**ため
手が出せずにいた。

## 4. 検証 — **数値が変わらないこと**

```
Rscript tests/pcap_fix_check.R      # 約1分、実データ不要
```

`examples/pcap_kernels.cpp` に**本家の実装そのままの写し**（`pcap_orig`）を
置いてあり、改変後の `secrad.r` の `pcap_poisson` と突き合わせる。

```
  [ 1] pcap_poisson  (min= 5)        最大絶対差 0          ← 完全一致
  [ 2] pcap_poisson  (min= 1)        最大絶対差 0          ← 完全一致
  ...
  [12] pcap_poisson  (min=10)        最大絶対差 0          ← 完全一致
```

**12通りすべて最大絶対差 0。丸め誤差すら出ない**（演算も順序も変えていないため）。

### 検証の設計で気をつけた点

**`ind_cov` の最小値が 1 以外（2 / 5 / 10）の場合を必ず混ぜてある。**
ここを 1 固定で試すと `cov_min` の値が効かず、「どちらも同じ」になるのが
当たり前で**検証になっていない**。

`smoke_test.R` も 28/28 成功。

**論文に「数値結果は完全に一致（最大絶対差 0）」と書く根拠が、
コマンド1つで再現できる状態になった。**

|---|---|---|---|---|---|
| 2,400 | 2.06秒 | 0.72秒 | 0.72秒 | 2.9倍 | なし |
| 4,800 | 5.74秒 | 1.87秒 | 1.83秒 | 3.1倍 | +2% |
| 9,600 | 21.22秒 | 3.83秒 | 3.55秒 | 5.5倍 | +8% |
| 19,200 | **83.09秒** | **7.68秒** | 7.02秒 | **10.8倍** | **+9%** |
| **指数** | **1.78** | **1.14** | 1.10 | | |

**指数が 1.78 → 1.14 とほぼ線形になった。** これが①の本質。
`nind` が大きいほど効くので、足環データの規模ではさらに伸びる。

**②が足すのは 4〜9% だけ。** 10.8倍と11.8倍なら実用上ほぼ同じ。

## 6. ②を見送った理由

①が「1語の差し替え」なのに対し、②は**ループの構造の組み替え**になる。

### 差分（`pcap_poisson`。①適用後の現状から）

```diff
- 	int i,j,k,colnum;
- 	double temp;
+ 	int i,j,k,base;
+ 	double acc;
  	int nmu=loglambda_mat.rows();
  	int neffort=effort_occ.size();
  	int nind=ind_cov.size();
  	const int cov_min = ind_cov.minCoeff();
  	MatrixXd res= MatrixXd::Zero(nmu,nind);
  	Eigen::setNbThreads(1);
- 	#pragma omp parallel for private(i,j,k,colnum,temp)
+ 	#pragma omp parallel for private(i,j,k,base,acc)
  	for(i=0;i<nmu;i++){
  		for(j=0;j<nind;j++){
+ 			acc = 0.0;
+ 			base = neffort*(ind_cov(j)-cov_min);
  			for(k=0;k<neffort;k++){
- 				colnum = k+neffort*(ind_cov(j)-cov_min);
- 				temp = dpoisson_c(detect(k,j),loglambda_mat(i,colnum)+log(srv(j,effort_occ(k)-1)),logprob);
- 				#pragma omp atomic
- 				res(i,j) += temp;
+ 				acc += dpoisson_c(detect(k,j),loglambda_mat(i,base+k)+log(srv(j,effort_occ(k)-1)),logprob);
  			}
+ 			res(i,j) = acc;
  		}
  	}
```

**正味 +2行**（追加6・削除4）。変わったのは4点:

| | 変更 | 理由 |
|---|---|---|
| 1 | `colnum` / `temp` → `base` / `acc` | 役割が変わった（`temp` は1回ぶんの値、`acc` は `k` の合計） |
| 2 | `base` を `j` のループで1回だけ計算 | `k` に依存しないのでここも**ループ不変**（①の同類） |
| 3 | 内側で `acc` に足し込む | **`res` への書き込みが `k` のループから消える** |
| 4 | `#pragma omp atomic` を削除し、`res(i,j) = acc` を1回 | 各スレッドは自分の `i` の行にしか書かないので**排他は元から不要** |

`pcap_bin` も同じ形（`dpoisson_c` が `dbin_c` になり `effort(k)` が増えるだけ）。

`pcap_poisson_debug` は `+=` ではなく `res(i,rescol) = temp;` で、
`(i, rescol)` は1回しか書かれない。**`#pragma omp critical`（全スレッド直列化）を
1行消すだけでよい**（未使用の関数なので実害は無いが、最も無駄が大きい箇所）。

> **⚠ `examples/pcap_kernels.cpp` の `pcap_fix2` は宣言を内側に書いている**
> （`for(int i=...)`、`double acc = 0.0;`）。**意味は同じ**で、そちらが実測した版。
> 上の差分は `secrad.r` の書き方（先頭でまとめて宣言し `private()` で並列化）に
> 合わせた最小差分。

### なぜ①より重いのか

①は**式の中の1語を、同じ値を持つ変数に置き換えただけ**で、
読む人は「この値は変わらないからループの外でよい」と1秒で確認できる。

②は**「何を・いつ・どこに書くか」が変わる**。`res` への書き込みが
最内ループから `j` のループへ移り、その正しさは「各スレッドが自分の `i` しか
触らない」という並列化の構造に依存する。**確認に手間がかかる。**

得られるのは 4〜9%。「本家との差分を小さく保つ」という
2026-09-14 の趣旨に照らして見送った。

### ⚠ 以前の主張の取り下げ

**「`atomic` があるとコア数を増やしても効率が落ちるので、
計算機増強の前提条件になる」と 2026-09-29 に一度書いたが、実測で否定された。**

`results/pcap_threads.csv`（`nmu` 400 / `nind` 2,400 / `neffort` 25）:

| スレッド | `orig` 効率 | `fix1` 効率 | `fix2` 効率 |
|---|---|---|---|
| 2 | 0.74 | 0.76 | 0.85 |
| 4 | 0.64 | 0.82 | 0.84 |
| **8** | **0.31** | **0.36** | **0.35** |
| 20 | **0.25** | 0.26 | **0.29** |

20スレッドで `orig` 0.25 対 `fix2` 0.29。時間比も 1スレッド 2.31 →
20スレッド 2.64 とほぼ横ばい。**`atomic` はスケーリングを支配していない。**

**8スレッドで効率が半減しているのは測定機の問題。**
編集機は Core i7-1370P（性能コア6 ＋ 効率コア8 / 20スレッド、28W級モバイル）で、
`#pragma omp parallel for` の既定の静的分割が全スレッドに均等な塊を配るため
**いちばん遅いコアを全員が待つ**。

> **この数字は均質なコアのマシンには転用できない。**
> 計算機センターの検討に使うなら、**解析機の32スレッドで測り直すこと**
> （`Rscript examples/pcap_threads.R --nind 2400 --rep 3`、数分。
> ただしクマの run と同時に走らせない）。
